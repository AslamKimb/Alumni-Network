# Environment variables

This project uses [varlock](https://varlock.dev). There is no `.env.example`, no `dotenv`, and no hand-maintained list of variable names in TypeScript. Each app ships a committed **`.env.schema`** that declares every variable, its type, and its validation rules. Values live outside git.

Read [DEPLOYMENT.md](./DEPLOYMENT.md) for the deploy itself. This page is only about env.

## The three layers

```
.env.schema          committed      names, types, rules. No secrets.
     +
values               not committed  local .env file, or Dokploy Environment tab
     ↓
varlock              validates + coerces at build and at boot
     ↓
src/env.ts           generated, gitignored, typed ENV object
```

Nothing in the app reads `process.env` for config except `PORT` (which the platform owns). Code imports `ENV` from `./env.server` (API) or uses `process.env.NEXT_PUBLIC_*` in the web app, where Next.js inlines it at build.

## The files

| Path | In git | What it is |
| --- | --- | --- |
| `apps/server/.env.schema` | **yes** | API schema. The source of truth. |
| `apps/server/.env` | no | Your local dev values. |
| `apps/server/src/env.ts` | no | Generated by `varlock codegen`. Never edit. |
| `apps/web/.env.schema` | **yes** | Web schema. |
| `apps/web/.env` | no | Local dev values. |
| `apps/web/src/env.ts` | no | Generated. Never edit. |
| `packages/db/.env.schema` | **yes** | Imports `NODE_ENV` + `DATABASE_URL` from the API schema. |
| `packages/db/src/env.ts` | no | Generated. Never edit. |

All three `.gitignore`s end with `!.env.schema` and `/src/env.ts` — that pair is what keeps the schema tracked and the generated file out.

## What the schema looks like

`apps/server/.env.schema` in full:

```
# @defaultRequired=true
# @defaultSensitive=true
# @currentEnv=$NODE_ENV
# @generateTsTypes(path=./src/env.ts, exposeEnv=local)
# ---

# @public @type=enum(development, production, test)
NODE_ENV=development

# @type=string(minLength=32)
BETTER_AUTH_SECRET=

# @type=url
BETTER_AUTH_URL=

# @type=url
CORS_ORIGIN=

# @type=string(minLength=1)
DATABASE_URL=

# Comma-separated emails granted admin while no active admin exists.
# @type=string
ADMIN_EMAILS=
```

The lines above `# ---` are **root decorators**, and they are the whole trick:

| Decorator | Effect |
| --- | --- |
| `@defaultRequired=true` | Every item is required. An empty value is an error, not `undefined`. |
| `@defaultSensitive=true` | Every value is redacted in logs and kept out of any client bundle. `@public` opts an item back in. |
| `@currentEnv=$NODE_ENV` | `NODE_ENV=production` also loads `.env.production` if it exists. No file, no problem. |
| `@generateTsTypes(path=./src/env.ts, exposeEnv=local)` | Generates a package-local typed `ENV`. `local` means no global type augmentation — each package owns its own. |

Per-item decorators do the validation:

- `@public` — not a secret, safe to inline into the browser bundle (`NODE_ENV`, `NEXT_PUBLIC_SERVER_URL` only).
- `@type=enum(development, production, test)` — anything else fails the load.
- `@type=url` — a bare `api.example.com` fails the load. It must be `https://api.example.com`.
- `@type=string(minLength=32)` — `BETTER_AUTH_SECRET` shorter than 32 chars fails the load.

`apps/web/.env.schema` is the same shape with two items: `NODE_ENV` (`@public`) and `NEXT_PUBLIC_SERVER_URL` (`@public @type=url`).

`packages/db/.env.schema` is one line of config:

```
# @import(../../apps/server/, pick=[NODE_ENV, DATABASE_*])
# @generateTsTypes(path=./src/env.ts, exposeEnv=local)
# ---
```

It imports the API's schema directory and picks only `NODE_ENV` and `DATABASE_*`. So migrations and the API can never disagree about which database they point at, and `drizzle-kit` needs no extra variables in the container.

## Where values come from, in order

Verified with `varlock explain CORS_ORIGIN` on this repo. Highest priority first:

| # | Source | Notes |
| --- | --- | --- |
| 1 | `process.env` | Anything the platform injects wins outright. |
| 2 | `.env.$NODE_ENV` | e.g. `.env.production`. Only if the file exists. |
| 3 | `.env.local` | Local overrides, gitignored. |
| 4 | `.env` | Base values. |
| 5 | `.env.schema` | Decorators and non-sensitive defaults only. |

`varlock load` prints the winning source next to each value:

```
✅ CORS_ORIGIN*  🔐sensitive
   └ ht▒▒▒▒▒  🟡 process.env
```

That `🟡 process.env` tag is why production needs no `.env` file at all: Dokploy's Environment tab sets real environment variables, and rule 1 does the rest. The `.env.schema` is still in the image, so validation and typing still apply.

`varlock explain <NAME>` shows every definition and which one is active:

```
Value source
  ⚡ process.env override (active)
  └ would use static value from .env without override
```

One nuance: the web app uses the Next.js integration, which swaps `.env.local` above `.env.$NODE_ENV`. This project ships no environment-specific files, so the two apps behave identically.

## Local development

Two files, both gitignored, created once by hand.

`apps/server/.env`

```
BETTER_AUTH_SECRET=nHKsXGncWs67QfXdcEUBpXK68cvwE7UM
BETTER_AUTH_URL=http://localhost:3000
CORS_ORIGIN=http://localhost:3001
DATABASE_URL=file:../../local.db

ADMIN_EMAILS=admin.one@example.com, admin.two@example.com
```

`apps/web/.env`

```
NEXT_PUBLIC_SERVER_URL=http://localhost:3000
```

Notes:

- `CORS_ORIGIN` is the web dev server (`3001`), `BETTER_AUTH_URL` is the API (`3000`). Swapping them breaks cookies and CORS.
- `DATABASE_URL` is relative to `apps/server`, so `file:../../local.db` lands at the repo root.
- `ADMIN_EMAILS` can be a comma-separated list with spaces. It only bootstraps an admin while no active admin exists.
- Generate a secret with `openssl rand -hex 32` (64 chars, comfortably over the 32 minimum).

Check that everything resolves before running anything:

```bash
cd apps/server && pnpm exec varlock load
cd apps/web && pnpm exec varlock load
```

`varlock load` exits `0` when valid and non-zero with a list of offenders when not. Add `--agent` for machine-readable JSON with sensitive values redacted.

Run the apps with `pnpm dev` (both) or `pnpm dev:server` / `pnpm dev:web`. The Next.js dev server prints a confirmation banner:

```
- Environments: .env, .env.schema,
                   ✨ loaded by varlock ✨
```

If that banner is missing, the `@next/env` override is not active — env values are not being validated.

## Production on Dokploy

**No `.env` file is committed.** One Dokploy Application holds this whole project, and its Environment tab is a single block: the API and web servers live in the same container, each reads what it needs from the same set of injected variables. varlock validates everything against the committed `.env.schema` at startup. Anything missing or malformed stops the container with a named error instead of booting a half-configured app.

Paste this into the app's Environment tab:

```
NODE_ENV=production
BETTER_AUTH_SECRET=replace-with-openssl-rand-hex-32
BETTER_AUTH_URL=https://api.example.com
CORS_ORIGIN=https://app.example.com
DATABASE_URL=file:/data/alumni.db
ADMIN_EMAILS=you@yourdomain.com
NEXT_PUBLIC_SERVER_URL=https://api.example.com
```

Rules that bite if you ignore them:

- **`app.example.com` and `api.example.com` must share a registrable domain.** Auth cookies are `SameSite=None; Secure`, which browsers reject across unrelated domains. `alumni.example.com` + `api.example.com` works; `alumni.vercel.app` + `api.example.com` does not.
- **No trailing slash** on `BETTER_AUTH_URL`, `CORS_ORIGIN`, or `NEXT_PUBLIC_SERVER_URL`. The URL type accepts it, but the client appends `/trpc` and you get `//trpc`.
- **`CORS_ORIGIN` is a single origin.** It is both the CORS allowlist and the only trusted Better Auth origin.
- **`ADMIN_EMAILS` cannot be empty.** The schema requires a value, and an empty string fails validation before the app starts.
- **`DATABASE_URL=file:/data/alumni.db`** is an absolute path inside the container. It only persists because `/data` is the `alumni-db` volume (see DEPLOYMENT.md).

### Build time vs runtime

| Variable | When it is read | Where it is set |
| --- | --- | --- |
| `NEXT_PUBLIC_SERVER_URL` | `next build` inlines it into the client bundle | Build Time Arguments (appears in the Environment tab once the Build Type is set to `Dockerfile`), and also as a normal env var so startup validation passes |
| `NODE_ENV` | Build and boot | Environment tab; the Dockerfile sets `production` as a fallback |
| `BETTER_AUTH_SECRET` | Boot | Environment tab → `${...}` in the `api` service |
| `BETTER_AUTH_URL` | Boot | Environment tab → `${...}` in the `api` service |
| `CORS_ORIGIN` | Boot | Environment tab → `${...}` in the `api` service |
| `DATABASE_URL` | Boot | Environment tab → `${...}` in `api` and `migrate` |
| `ADMIN_EMAILS` | Boot | Environment tab → `${...}` in the `api` service |

Changing a runtime variable needs a redeploy (container recreate). Changing `NEXT_PUBLIC_SERVER_URL` needs a **rebuild**, because the old value is already baked into the JavaScript the browser downloads. Setting it only at runtime is the most common way to ship a web app that still calls `localhost`.

## Changing the schema

`src/env.ts` is generated and gitignored, so it is rebuilt in three places: your machine (`postinstall`), the Docker build (`RUN pnpm env:generate`), and any platform that runs `pnpm install` for you. After editing any `.env.schema`:

```bash
pnpm env:generate
```

Then commit the schema change. The generated file stays untracked; type errors that mention `ENV.SOMETHING` almost always mean this command has not run since the schema changed.

Adding a variable is three steps: declare it in the `.env.schema` with a type, set it locally in `.env`, set it in the Dokploy Environment tab. Miss the last one and the container refuses to start — which is the point.

## Failure modes

Each of these was reproduced locally.

| What you see | Cause | Fix |
| --- | --- | --- |
| `Value is required but is currently empty` (one line per variable) | Nothing supplied the value | Set it in `.env` or the Environment tab |
| `Invalid URL` | `api.example.com` instead of `https://api.example.com` | Add the scheme |
| `[varlock] Invalid env vars: A, B` then exit code `1` | Validation summary | Fix every name listed |
| `[varlock] No .env files found in <dir>` then `LibsqlError: URL_INVALID` | Running from a directory with no `.env.schema` | Run from the package directory, or ship the schema in the image |
| Container restarts in a loop with a varlock error | Environment tab is missing a variable | Read the name in the log, add it, redeploy |
| Value is in the Environment tab but the container still says it is empty | Not referenced by the container at all — never reached it | Confirm the name is spelled exactly as deployed (no spaces, no quotes) |
| Web app calls `localhost:3000` in production | `NEXT_PUBLIC_SERVER_URL` set at runtime only | Set it as a build argument and rebuild |
| Everyone logged out after a deploy | `BETTER_AUTH_SECRET` changed | Expected. Rotating the secret invalidates all sessions. |

## Secrets

- Every value is `@sensitive` by default, so `console.log` output is automatically masked (`nH▒▒▒▒▒`) at runtime, and varlock refuses to send a sensitive value to the browser.
- `varlock load --agent` and `varlock explain` never print full secrets. Use `varlock reveal BETTER_AUTH_SECRET` when you genuinely need to read one; it renders in the alternate screen buffer so it stays out of your scrollback.
- Only `NODE_ENV` and `NEXT_PUBLIC_SERVER_URL` are `@public`, so those are the only two values that can end up in the JavaScript bundle.
- Rotate `BETTER_AUTH_SECRET` by generating a new value, updating the Environment tab, and redeploying. Accept that it logs everyone out.
- Never commit a `.env` file. If one lands in git, rotate every value in it — the history keeps it forever.
